TL;DR

Your bank shows you a balance, not ten thousand transactions to add up. Your platform's documentation should work the same way.

A platform's PRDs and specs are the transactions — the ledger. “How does this work today?” is the balance, and most organizations never materialize it, so every engineer — and now every AI agent — has to reconstruct it by hand. Agents make this worse: they read constantly and take stale documents literally.

The fix is a living representation of reality: one current, shared, capability-organized description of what's true now, kept beside the code. In June 2026 Google Cloud published the Open Knowledge Format (OKF), effectively naming and standardizing that source of truth — a vendor-neutral bundle of small markdown concept files (the balance) with a built-in log.md (the ledger).

Treat each PRD as a transaction — a delta against the balance — and fold it back as part of the definition of done. But a format is only a shape; standardized deltas and an enforced lifecycle are the heartbeat that keeps it true. Do this and knowledge stops being development's exhaust and becomes a first-class deliverable — the company's digital memory, read the same way by every human and every agent.

01 · The everyday truth

You already understand this, because you have a bank account

Your account keeps a ledger — every transaction since it opened, in order, never edited. And it shows you a balance — one number that says what you have right now. The balance is simply the ledger, added up. You could recompute it from the full history every time… but you never do. The bank keeps it computed and shows it first.

02 · The problem

Software makes you add up the transactions yourself

“How does Customer Authentication actually work today?”

It's the most reasonable question in the world — and there is nowhere to read the answer. Instead there is an archive, and the truth is smeared across years of changes, most of them partly undone, none of them labelled “superseded, don't trust me.” To answer, an engineer must find every document that ever touched authentication and merge them in their head. That isn't engineering. It's archaeology.

Abundant documentation, and still no balance. A pile of transactions is not a representation of reality.

The mistake has a name from Part I: a ledger — a history of decisions — is being used as a balance — a representation of reality. Most teams think they lack documentation. They don't. They're drowning in it. What they lack is one current place that says: this is how it works now.

03 · What changed

The heaviest reader is no longer human

The archaeology used to be survivable because the archaeologist was a person — who skims, infers, and knows which old doc to distrust. That reader is now outnumbered. The main consumer of organizational knowledge is an AI agent, and it reads on every task and takes stale documents literally.

Yesterday's reader

A human, occasionally

Reads now and then. Fills gaps from experience. Tolerates a little rot.

Sparse reads · forgiving
Today's reader

Agents, constantly

Reads on every change, review, and test. Takes what it's given literally — then writes code on it, at speed.

Constant reads · literal

Agents reason best on knowledge that is consistent, structured, current, and small — the properties of a balance, not a ledger.

04 · Why the obvious fixes fail

Every team reaches for the same three, and each one mistakes navigating the ledger for materializing the balance

✕

“Just point the AI at all the PRDs”

Feed the model the whole corpus and let retrieval find the relevant history per question.

Recompute-from-ledger in an ML coat. Retrieval makes the archive searchable, not current — it hands the model a superseded proposal next to the change that killed it and lets it guess.
✕

“Hand-tune a prompt per assistant”

One system prompt for the coder, another for the reviewer, another for the tester.

The balance, forked N ways. Each prompt is a private, drifting photocopy of the same truth — the exact divergence, reintroduced one layer up.
✕

“Let knowledge fall out of the work”

Whatever docs happen to drop out of shipping a feature become the record.

The balance as exhaust. Nobody owns it, so nobody keeps it current, so it rots — and an agent acting on rot with confidence is worse than one reading nothing.

Cross-referencing the ledger, however richly, never produces the balance. Reference is not aggregation.

05 · The named source of truth

Google gave the balance an official shape: OKF

For as long as spec-driven development has been standard practice, teams still improvised where current truth lived — a wiki here, a docs folder there, a prompt pasted into each assistant. In June 2026, Google Cloud published the Open Knowledge Format (OKF), effectively naming and standardizing that source of truth: a vendor-neutral bundle of small markdown concept files that humans and agents read the same way.

The quietly remarkable part, for a reader of Part I: OKF already ships the balance-and-ledger split. Concept files are the balance. A built-in log.md is the ledger. An index.md is the map you read before the territory.

/knowledge/ # the balance — living reality (OKF bundle)
├─ index.md # the map: capabilities & entry points
├─ auth/
│ ├─ customer-authentication.md # concept — how it works NOW
│ ├─ session-management.md
│ └─ log.md # local change history (the ledger)
├─ payments/
│ ├─ payment-intent.md # + YAML front matter: owner, links
│ └─ settlement.md
└─ domain/
├─ account.md # entity + invariants
└─ customer.md
concept file = the balance log.md = the ledger index.md = the map

Just files. No runtime, no SDK, no lock-in — and it lives beside the code, where the balance belongs.

Just files

No runtime, no SDK, no proprietary account. Renders on GitHub, ships as a tarball, mounts on any filesystem.

Vendor-neutral

Not chained to a cloud, database, or model. The same bundle feeds a coding agent, a reviewer, a test generator, and a human.

Legible to both

Markdown for the person; YAML front matter and links for the machine. One artifact, two readers, no translation layer.

Ships the split

Concept files are the balance, log.md is the ledger, index.md is the map — Part I's architecture, built in.

07 · The mechanism

Every PRD is a transaction, folded back into the balance

Stop treating a PRD as a destination; treat it as a delta against the balance. A change starts from the living representation of reality — which already holds the domain, the APIs, the rules — and expresses only what changes. When it ships, the change is folded back: the affected concepts are edited to their new truth. The fold is paid once, by the person with context — not by every future reader, forever.

Pay the fold once, at write time — the way a bank updates your balance the instant money moves.

A change isn't done until the balance reflects it. A practical definition of done binds the two together:

1 · Code merged

The behavior actually ships.

2 · Concepts edited

The affected OKF nodes are overwritten to their new truth.

3 · Decisions & history filed

Significant “why” goes to an ADR; the PRD is archived and noted in log.md.

4 · Enforcement passes

A contract test or fitness function breaks when the balance and the system disagree.

08 · The catch

A format is a shape, not a heartbeat

A perfectly valid OKF bundle can be perfectly out of date. The format guarantees portability and structure — it guarantees nothing about truth. Truth is a property of process.

OKF The shape

A vendor-neutral form for the balance. Portable, structured, readable by human and machine. Necessary — but inert on its own.

Process The heartbeat

Standardized deltas + an enforced delivery lifecycle. The fold-back is part of the definition of done, bound to a signal — so skipping it breaks something instead of silently rotting the truth.

The bank has both: a standard for the balance, and machinery that updates it when money moves.

09 · What it costs

Honest trade-offs — none of this is free

The story would be dishonest if it pretended the balance maintains itself. Each risk has a mitigation, but each needs deliberate attention.

Keeping the graph current is real work

More moving parts than one big doc. Mitigate: derive everything derivable from code; make the fold-back part of done.

The balance is a contended, shared artifact

Many teams editing one representation of reality creates coupling. Mitigate: clear ownership per concept, recorded in front matter.

Enforcement is the crux

It all collapses without a signal when balance and system disagree — harder for prose than for generated contracts. Mitigate: be honest about which nodes are enforced.

Writing good deltas is a skill

It only pays off once the balance is trustworthy to diff against — a chicken-and-egg. Mitigate: bootstrap the baseline on purpose.

OKF v0.1 will change

An early spec, still moving. Mitigate: bet on the idea — a neutral, file-based balance beside the code — and keep coupling loose.

The boundaries are judgment

Where balance ends and mere history begins is a matter of taste. Mitigate: a light convention (concept vs. log.md), not a formula.

10 · Do this

Give the balance a place to live, and a pulse

Adopt the balance-not-ledger model, and turn knowledge from development's exhaust into a first-class deliverable — the company's digital memory, read the same way by every person and every agent.

  • 1Materialize the representation of reality as a living knowledge graph — small, connected concept files, beside the code, in a neutral shape like OKF.
  • 2Make every PRD a transaction against the balance, and fold it back as part of the definition of done.
  • 3Derive from code where you can, enforce the rest in CI — so the balance can't drift in silence.
  • 4Evict, don't delete, the ledger — keep history indexed and one link away.
  • 5Represent once, consume everywhere — one graph, retiring the drawer full of per-assistant prompts.

The engineer deserves to type her question and read one current file — one link from its history. The same way every bank in the world already shows you your money.
