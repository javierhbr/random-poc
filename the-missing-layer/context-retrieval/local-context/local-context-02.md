This second part incorporates the relationship between the platform's functional reality and the functional reality of each component derived from the source code.

Process for building and tracing functional context

1. Two complementary levels of context

The process maintains two levels of documentation that serve different purposes but must remain connected:

1. Platform functional context, built from requirements, features, flows, and experiences.
2. Component functional context, built through reverse engineering from the source code.

The platform context describes the experience and general behavior that the platform offers its users.

The component context describes how each service, process, application, or artifact participates in implementing those capabilities.

The combination of both levels makes it possible to understand not only what the platform does, but also which components support each feature and what specific behaviors exist within them.

⸻

2. Building the platform's current reality

The current reality is generated by accumulating, reconciling, and consolidating the features described across multiple requirements documents.

Each document can represent:

* A new feature.
* A change to an existing feature.
* An improvement to an experience.
* A modification to a flow.
* A new business rule.
* An exception.
* An integration.
* The evolution of an existing capability.

These documents usually describe individual changes that occurred at different points in time. On their own, they do not necessarily represent the platform's complete and current behavior.

For this reason, the process does not simply consist of storing all requirements, but of integrating them to build a coherent representation of how the platform currently works.

The current reality is the accumulated result of:

* Original features.
* Subsequent changes.
* Extensions.
* Corrections.
* Exceptions.
* New scenarios.
* Current functional decisions.

The result becomes the platform's functional source of truth.

⸻

3. The current reality as the source of truth

The consolidated documentation represents the platform's known and current behavior.

Its purpose is to answer questions such as:

* What experiences does the platform offer?
* What can each type of user do?
* How does a given flow work?
* What business rules apply?
* What scenarios are supported?
* Which components participate?
* Which external systems are involved?
* What are the downstream dependencies?
* What happens under normal and exceptional conditions?

Requirements documents remain as historical evidence and as a reference for specific decisions.

However, the primary source of context for agents and models must be the consolidated representation of reality, not the raw sum of historical documents.

⸻

4. Identification of components and artifacts

As part of building the platform context, all components and artifacts that participate directly or indirectly in its features are identified.

This can include:

* Web applications.
* Mobile applications.
* Backend services.
* Microservices.
* APIs.
* Batch processes.
* Event processors.
* Workers.
* Relevant databases.
* Integration systems.
* External platforms.
* Third-party services.
* Downstream systems.
* Upstream systems.
* Repositories with functional logic.
* Automated operational processes.

The relationship between the feature and the components must be part of the platform context.

For example, a feature such as credit card payment may involve:

* The application used by the customer.
* An API gateway.
* A payment service.
* An account service.
* An external processor.
* An anti-fraud system.
* A notification service.
* Reconciliation processes.
* Downstream reporting or accounting systems.

The platform context identifies this relationship at a general level. Afterward, each component with code can be analyzed independently and in greater depth.

⸻

5. Reverse engineering of components

To build the specific context of each service, process, or component, an Uncle Dev command is used that runs a reverse engineering process on the source code.

At this stage, the code is indeed used as the primary source of evidence.

However, the goal of the analysis is not to document the code line by line or generate a description of classes, methods, or files.

The goal is to reconstruct the functional behavior implemented by the component.

Reverse engineering should help discover:

* What features the component implements.
* What use cases it supports.
* What business rules it executes.
* What special scenarios it handles.
* What validations it applies.
* What inputs it receives.
* What outputs it produces.
* What events it consumes or publishes.
* What APIs it exposes or invokes.
* What processes it executes.
* What dependencies it has.
* What errors or exceptions it handles.
* What functional states it manages.
* What platform capabilities it supports.

The result should be a functional specification derived from the code, not low-level technical documentation.

⸻

6. Feature-oriented reverse engineering

Reverse engineering is performed following the Spec-Driven Development methodology defined for the project and using Uncle Dev's capabilities.

The process must interpret the code from a functional perspective.

Instead of asking:

What classes and methods exist in this repository?

The analysis should ask:

What behaviors, rules, and business capabilities are implemented in this repository?

For example, instead of documenting only that a method exists called:

processCreditCardPayment()

the result should functionally explain:

* What conditions allow a payment to be made.
* What validations are applied.
* What types of payment are supported.
* What happens when the payment is rejected.
* How retries are handled.
* What external systems are involved.
* What events are generated.
* How the result is reported to the user.
* What downstream processes are triggered.

⸻

7. Complement between platform documentation and code

Reverse engineering should not be performed in isolation.

The component analysis must be complemented with the platform's functional context.

The platform context provides:

* The business intent.
* The purpose of the feature.
* The expected experience.
* The actors involved.
* The main flows.
* The known rules.
* The official terminology.
* The requirement identifiers.
* The relationship with other domains and components.

The code provides:

* The behavior actually implemented.
* The real validations.
* Undocumented scenarios.
* Exceptions.
* Variants.
* Technical dependencies.
* Alternative flows.
* Logic accumulated over time.

Combining both sources makes it possible to identify:

* Functionality that is documented and implemented.
* Functionality that is documented but not found in the code.
* Functionality that is implemented but not documented.
* Differences between expected and actual behavior.
* Component scenarios that don't appear in the high-level description.
* Duplicated or contradictory rules.
* Possible obsolete capabilities.
* Unknown dependencies.

⸻

8. Traceability via requirement tags

To maintain traceability between the platform's reality and the implementation of components, features use requirement identifiers or tags.

These tags make it possible to connect:

* The original requirement.
* The consolidated platform feature.
* The user flow or experience.
* The bounded context.
* The responsible component.
* The specification obtained through reverse engineering.
* The specific scenarios implemented in the code.
* Related tests.
* Downstream dependencies.

A high-level feature can have a primary identifier.

For example:

ER-PAYMENT-001

This identifier can represent the general capability:

Make a credit card payment.

Within a specific component, that feature can be expanded using subtags.

For example:

* ER-PAYMENT-001.01: Payment from an internal account.
* ER-PAYMENT-001.02: Payment from an external account.
* ER-PAYMENT-001.03: Scheduled payment.
* ER-PAYMENT-001.04: Recurring payment.
* ER-PAYMENT-001.05: Funds validation.
* ER-PAYMENT-001.06: Payment rejection.
* ER-PAYMENT-001.07: Processing retry.
* ER-PAYMENT-001.08: Cancellation of a scheduled payment.
* ER-PAYMENT-001.09: Result notification.
* ER-PAYMENT-001.10: Subsequent reconciliation.

The main identifier maintains the relationship with the platform capability.

The subtags allow documenting the functional detail that is only visible when analyzing the component.

⸻

9. Feature hierarchy

Traceability can be organized through a functional hierarchy.

Level 1: Platform experience or capability

Represents what the platform offers the customer.

Example:

ER-PAYMENT

Experience: Payment management.

Level 2: Main flow or feature

Represents a specific action or result within the experience.

Example:

ER-PAYMENT-001

Feature: Make a credit card payment.

Level 3: Functional scenario

Represents relevant variants of the main flow.

Example:

ER-PAYMENT-001.02

Scenario: Make the payment from an external bank account.

Level 4: Component-specific behavior

Represents a rule, validation, or internal processing that needs its own traceability.

Example:

ER-PAYMENT-001.02.03

Behavior: Reject the payment when the external account has not been verified.

This hierarchy makes it possible to navigate from a general platform capability down to a concrete behavior implemented within a component.

⸻

10. Level of detail per context

The level of detail should not be the same across all documents.

Platform context

Should describe:

* The general experience.
* The main flows.
* The visible capabilities.
* The actors.
* The relevant business rules.
* The expected results.
* The participating components.
* The main dependencies.

Its goal is to provide a coherent and understandable view of the platform.

Component context

Should describe:

* The implemented scenarios.
* The specific validations.
* The flow variants.
* The rules executed by the component.
* The concrete integrations.
* The states managed.
* The events.
* The exceptions.
* The retries.
* The functionally relevant internal behaviors.

Its goal is to explain, with greater precision, how the component contributes to the platform's capabilities.

⸻

11. Example: credit card payment

At the platform level, the feature could be documented as follows:

ER-PAYMENT-001: Credit card payment

The customer can make a payment against their credit card balance using a valid funding source. The platform validates the request, processes the payment, reports the result, and updates the corresponding status.

This description represents the expected general behavior.

However, the payment service may contain a considerable number of additional scenarios:

* Full payment.
* Minimum payment.
* Payment for a custom amount.
* Immediate payment.
* Scheduled payment.
* Recurring payment.
* Payment from an internal account.
* Payment from an external account.
* Unverified external account.
* Insufficient funds.
* Duplicate payment.
* Payment rejected by the processor.
* Automatic retry.
* Cancellation of a scheduled payment.
* Modification of a pending payment.
* Reversal.
* Reconciliation.
* Partial error.
* Dependency timeout.
* Successful or failed notification.

Not all of these details need to appear in the platform's high-level description.

However, they must be documented within the component's functional context and connected to the main feature through tags and subtags.

⸻

12. Mapping between platform and components

Once reverse engineering is complete, a mapping process is performed between:

* The features identified in the platform's reality.
* The features found within each component.
* Scenarios derived from the code.
* Dependencies between components.

The mapping can be represented through a matrix such as the following:

Tag	Feature	Bounded Context	Component	Relationship Type	Status
ER-PAYMENT-001	Card payment	Payments	Customer App	Initiates the flow	Mapped
ER-PAYMENT-001	Card payment	Payments	Payment API	Orchestrates the flow	Mapped
ER-PAYMENT-001.05	Funds validation	Payments	Account Service	Validates funds	Mapped
ER-PAYMENT-001.06	Payment rejection	Payments	Payment Processor	Processes rejection	Mapped
ER-PAYMENT-001.09	Notification	Notifications	Notification Service	Reports the result	Mapped
ER-PAYMENT-001.10	Reconciliation	Payments	Settlement Batch	Reconciles the payment	Mapped

The relationship is not necessarily one to one.

A feature can involve multiple components, and the same component can support multiple features.

⸻

13. Results of the reverse engineering process

The process applied to each component must produce at minimum:

13.1 Component functional specification

Describes what the component does from a functional standpoint.

13.2 Feature map

Lists the platform features supported by the component.

13.3 Scenario catalog

Documents the main, alternative, and exceptional cases.

13.4 Business rules

Identifies the rules found in the implementation.

13.5 Integration map

Describes the related upstream and downstream systems.

13.6 Traceability map

Relates platform tags to concrete component behaviors.

13.7 Detected differences

Records divergences between existing documentation and the behavior found in the code.

13.8 Open questions

Identifies ambiguous behaviors that require human validation.

⸻

14. General process flow

The complete flow can be summarized as follows:

1. Collect requirements documents.
2. Organize documents by domain, experience, and flow.
3. Consolidate accumulated features.
4. Build the platform's current reality.
5. Assign traceability tags to features.
6. Identify all related components and dependencies.
7. Locate the repositories that contain code.
8. Run reverse engineering with Uncle Dev.
9. Analyze the code with a functional focus.
10. Complement the analysis with the platform context.
11. Map the features found against existing tags.
12. Create subtags for detailed component scenarios.
13. Detect differences and gaps.
14. Validate the results.
15. Publish the component documentation.
16. Update Local Search.
17. Keep the platform context synchronized with the component contexts.

⸻

15. Core principle

The core principle of the process is:

Platform documentation explains the functional reality from the business and customer perspective. Documentation derived from the code explains how that reality is supported, distributed, and expanded within the components.

Neither perspective is sufficient on its own.

Platform documentation without code analysis can omit scenarios that are actually implemented.

Code documentation without platform context can describe behaviors without explaining their purpose, meaning, or relationship to the user experience.

The complete source of truth emerges from the traceable connection between both.

In the next iteration, it would be worth defining how differences between documented reality and reality found in the code are detected and resolved, including who has authority to update each level.
